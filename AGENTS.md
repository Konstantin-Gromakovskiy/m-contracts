# Контракты TypeSpec

## Структура

- Контракты сервиса хранятся в `service/<service-name>/`.
- У каждого сервиса есть `main.tsp` для импортов и `service.tsp` с декларацией `@service` и базовым маршрутом.
- Операции и модели группируются по доменам внутри сервиса, например `service/identity/employees/`.
- В `service/common/` размещаются только технические примитивы, общие для нескольких сервисов. Доменные модели не выносятся туда только из-за текущего сходства.
- Каждый сервис импортируется в корневой `main.tsp`, чтобы войти в основную сборку.
- `PlaygroundService` -- учебный сервис, включённый в основную сборку. Он демонстрирует возможности TypeSpec, но не является продуктовым API.

## Именование

- Корневой namespace совпадает с именем сервиса: `IdentityService`, `BookingService`, `PaymentService`.
- Файлы домена используют дочерний namespace, например `IdentityService.Employees`.
- Модели запросов называются в соответствии с контрактом, например `CreateEmployeeCommand`.
- При документировании текущего API сохраняйте прежние имена операций и значения `@operationId`.

## Документация

- Используйте `@summary` для короткого описания, а `@doc` -- для подробностей в CommonMark Markdown. Документируйте публичные операции, модели и значимые свойства моделей.
- Для групп операций добавляйте `@tag` на интерфейс и `@tagMetadata` на service namespace. Описание из `@tagMetadata` отображается в Scalar у группы ручек.
- Добавляйте `@example` к моделям, когда пример делает формат запроса или ответа понятнее.
- Используйте `examples.tsp` с `const` и `@opExample` только когда автоматического примера недостаточно или нужен конкретный пример ответа.
- Для явных примеров ответов с массивом объектов используйте `@opExample` с полным `returnType`: Scalar может не применить `@example` модели к элементу массива.
- Используйте `@operationId` для стабильного идентификатора операции и `@externalDocs` для ссылок на внешнюю документацию при необходимости.

## Точность Контракта

- JSON-тело ответа моделируется явно через `@body`.
- Для UUID используется `Primitives.Uuid`.
- Ошибки добавляются в контракт только когда известен их фактический формат передаваемых данных.

## Публикация В Scalar

- Основная сборка создаёт отдельную спецификацию для каждого сервиса: `tsp-output/schema/openapi.<service>.json`.
- При добавлении сервиса добавьте его в `sources` в `web/index.html`, чтобы он был доступен в селекторе Scalar.
- Добавьте сгенерированную спецификацию в `Dockerfile`, чтобы сервис был доступен в опубликованном интерфейсе.
- Файлы в `tsp-output/` генерируются компилятором и не редактируются вручную.

## Проверка

- После каждого изменения контракта запускайте `npm run compile` из директории `contracts/`.
- В каждой изменённой `tsp-output/schema/openapi.<service>.json` проверьте пути, `operationId`, схемы и типы содержимого.
- Для разработки с автоматической пересборкой и обновлением Scalar используйте `npm run dev`.
